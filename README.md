MCPD Agent — Private-First Intelligent Document Agent


Hackathon submission · Answers questions from your private local documents first, then reaches the public internet only when necessary — powered by encoderfile, llamafile, and a custom MCPD routing engine.

What it does

MCPD Agent is a locally-run AI assistant that keeps your documents private. When you ask a question, it searches your own files first using semantic vector search. Only if your documents don't contain a good answer does it reach out to the web — and even then, the final answer is generated by a local LLM running entirely on your machine. No data leaves your environment unless you ask for something time-sensitive.

Key features

1. Smart query classifier

Every query is classified across three dimensions before any tool is invoked:


doc_intent — mentions of runbook, architecture, API spec, readme, etc.
time_sensitive — latest news, current trends, 2026 queries
conceptual — why/how/explain questions that benefit from reasoning


This means the agent never wastes a web search on something already in your documents, and never answers a time-sensitive question from stale local data.

2. Relevance-gated RAG

Most RAG agents blindly pass whatever FAISS returns to the LLM, leading to hallucinated answers built on irrelevant chunks. MCPD Agent scores retrieved context against the query before deciding to use it:


Counts meaningful keyword hits (filters stop words under 4 chars)
Applies a penalty for boilerplate/noise chunks
Rejects context scoring below threshold, triggering the next tool in the chain


For doc-intent queries (e.g. "summarize runbook"), FAISS retrieval is trusted directly — the relevance gate is bypassed because the document was explicitly named.

3. Three-tier fallback chain

Local docs → Web search → LLM reasoning → Graceful fallback

Each tier only activates when the previous one fails or is inappropriate. This prevents over-reliance on any single tool and keeps responses grounded.

4. Fully local and private by default


Embeddings generated via encoderfile — no external embedding API
Inference via llamafile at localhost:8080 — no cloud LLM calls
Web search only triggers for explicitly time-sensitive queries
Your documents never leave your machine


5. Graceful LLM error handling

If the local llamafile instance is unavailable or times out, the agent surfaces a clear, actionable error message rather than crashing or returning a confusing stack trace.


Tech stack

Embeddings - encoderfile - Converts document chunks to vectors locally
Vector store - FAISS - Fast similarity search over embedded chunks
Local LLM - llamafile (Qwen) - Generates all answers on-device
Web search - DuckDuckGo (ddgs) - Public internet fallback
Routing MCPD engine (custom) - Classifies queries and dispatches to the right tool

Design decisions

Why not always search the web? Privacy. Your documents may contain internal architecture, API keys patterns, or proprietary runbooks. Defaulting to local-first ensures sensitive content is never part of a web-augmented prompt.

Why a relevance gate? Without it, the LLM hallucinates confidently from unrelated chunks. The gate forces the agent to be honest about what it knows locally before fabricating an answer.

Why classify queries before retrieval? Different query types need different tools. A question about "latest trends" should never block on a FAISS search that will always score low — classifying first makes routing fast and predictable.
